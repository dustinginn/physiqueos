## Audit and proof of the collision mechanism (not inferred from the log string)

Traced every layer client-side and server-side:

1. **Native identity construction** (`HealthKitObservationNormalizer.normalize`): for `.activitySummary`/`.nutritionDailyTotal` payloads, the external id is `"<type>:<namespace:>?<localDate>"`. `HealthKitBatchBuilder.build` selected the namespace only via `scope.predicateVersion.hasPrefix(HealthKitCanonicalTestDay.predicatePrefix)` — the canonical-test-day path got `"testday"`; every other caller (canary AND automatic) got `nil` (no namespace).
2. **Three known `predicateVersion` families**, confirmed by reading `HealthKitFounderCanaryModels.swift` and `HealthKitAutomaticSynchronizationCoordinator.swift`: canary validation-only (`healthkit-activity-validation-only-v1:<start>:<end>`, purpose `validation_only`, no namespace), canonical test day (`healthkit-canonical-testday-v1:<date>`, purpose `operational`, namespace `testday`), automatic (`healthkit-automatic-v1`, purpose omitted -> `operational` by the Server's default, no namespace before this fix).
3. **The collision**: canary and automatic both produced the bare `activity-summary:<date>` for the same day, under different purposes. The Server's persistence layer (`CanonicalPersistenceCommandPorts.js`) fetches the existing stored record for that exact external-id-derived identity and, if `(stored.ingestionPurpose ?? "operational") !== observation.ingestionPurpose`, rejects with 409 `HEALTHKIT_INGESTION_PURPOSE_IMMUTABLE`. Confirmed by reading that exact code path, not merely the log string.
4. **Live production evidence** (already captured in the prior task, reconfirmed here): the 409 at 2026-09-22T18:08:25Z is consistent with exactly this mechanism.
5. **The permanent-block mechanism**: `HealthKitSynchronizationEngine.deliverPending` re-threw immediately on encountering an already-`.rejected` partition, never retiring it; `synchronize()`'s top-level check never re-queries HealthKit while any batch is pending. Traced every mutator of `authoritativeCursor` (`finalizeIfReady`, `resetCursorForBoundedRecovery`) and confirmed a rejected batch's cursor is never promoted — the data was never lost, only permanently unreachable without a code fix.

## Design and fix

**1. Automatic-ingestion identity namespacing.** Added `HealthKitBatchBuilder.externalIDNamespace(for: predicateVersion) -> String?`, a single pure, exhaustively-testable function mapping every known caller to a distinct namespace: canonical-test-day keeps `"testday"`; the new automatic coordinator gets `"automatic"` (`HealthKitAutomaticSynchronizationCoordinator.externalIDNamespace`); the canary's validation-only predicate versions are deliberately left un-namespaced -- that bare format is the original V1-compatible identity, and it is every other caller that must now avoid it, not the canary that should change retroactively. Satisfies every stated requirement: deterministic (pure function of `predicateVersion` + `localDate`, no random UUID), foreground and background converge on the identical scope/predicateVersion (unchanged by this fix) so they naturally converge on the identical automatic identity, Activity and Nutrition never collide with each other (different string prefixes, unaffected), no historical migration needed (namespacing only changes what NEW identities look like going forward).

**2. Permanent-rejection recovery.** Added `HealthKitSynchronizationStore.abandonPendingBatch(batchID:code:at:)`: removes the batch from `pendingBatches` entirely, records the reason/timestamp into three new optional `HealthKitStreamDiagnostics` fields (`lastAbandonedBatchCode`, `lastAbandonedAt`, `abandonedBatchCount` -- optional so decoding an already-poisoned Build 51 envelope that predates this field never fails), and, critically, does **not** touch `authoritativeCursor`. `deliverPending` now calls this immediately on (a) encountering an already-persisted `.rejected` partition, or (b) a fresh `.rejected` result from the uploader -- in both cases still honestly throwing to report *this* attempt as failed, but leaving `pendingBatches` empty so the *next* `synchronize()` call re-queries HealthKit fresh instead of hitting the same dead end. Because the cursor never advanced past the abandoned data, the real HealthKit content resurfaces as a fresh "addition" (its fingerprint was never recorded as "already seen") and gets re-submitted under the now-corrected, namespaced identity -- this is what makes an already-poisoned Build 51 device self-heal on the very next ordinary foreground, with no migration step and no reinstall. `markRejected` is now unused by the engine (superseded by `abandonPendingBatch` in both of its former call sites); left in the protocol as a harmless, still-valid lower-level primitive rather than removed, to minimize the diff.

**Server:** confirmed, by reading `HealthKitObservationService.js`'s `normalizeObservation`/`requiredText` and `CanonicalPersistenceCommandPorts.js`, that the Server treats `externalId` as a fully opaque string (validated only for non-emptiness, then hashed into an identity tuple) -- grepped the entire Server source for any parse/split/regex/pattern-match against `externalId` and found none. **No Server change was needed or made.** Separately confirmed, by reading `HealthKitCanonicalDayService.js`, that canonical Activity/Nutrition days are keyed only by `(domain, localDate)` via `getHealthKitCanonicalDayRecordId`, completely independent of which raw external identity contributed the observation, and that `reconcileHealthKitCanonicalDay`'s own documented behavior for an unorderable, differently-sourced snapshot is "the existing canonical day is kept and the newcomer stays raw (never a silent overwrite)" -- i.e. the reconciliation layer cannot produce a duplicate canonical day regardless of how many distinct external identities (canary's bare id, the new `...:automatic:<date>` id) ever contribute to the same day.

## Independent review

Ran a second fresh-context adversarial review (separate model context, given the full worktree and the diff against c6381243, with the same numbered-checklist approach as the prior task). **Verdict: APPROVE, no blocking issues.**

Key confirmations, each independently traced through the source rather than taken on faith: `abandonPendingBatch` genuinely never touches `authoritativeCursor` (verified the only two writers of it, `finalizeIfReady` and `resetCursorForBoundedRecovery`, and that `abandonPendingBatch` calls neither) -- and precisely worked out what WOULD go wrong if it did (the abandoned day's fingerprint would be remembered as "already seen," silently and permanently suppressing that day's real data, worse than the original bug); the known-collision retry loop is genuinely broken by the namespace fix (the rebuilt batch gets a new identity, so no second 409); `markRejected` is confirmed unreachable from the engine and correctly kept in the protocol only because real Build 51 envelopes on disk still contain that state and a test needs to reproduce it; every crash-recovery point converges correctly; and the blast radius is confirmed limited to the intended files with Workout canary, Sandbox isolation, and authorization scope all untouched.

Five real findings I incorporated before finalizing (none blocking, all closed):
1. **Exhaustiveness gap**: `externalIDNamespace(for:)` didn't register the Workout canary's `predicateVersion` prefix at all (harmless today since Workout observations always carry a real `healthKitUUID` and never reach the daily-aggregate branch, but the doc comment overclaimed "every caller"/"three callers"). Fixed: registered `HealthKitWorkoutCanaryDay.externalIDNamespace = "workoutcanary"`, corrected the comments to state the exhaustiveness claim precisely (a closed, explicit switch -- not a mechanism that can detect its own incompleteness -- and that daily-aggregate *deletions* are a separate, still-open, currently-dormant follow-up).
2. **Near-tautological test**: the original background/foreground convergence test used `.activeEnergy` (a UUID-bearing stream that bypasses the namespace branch entirely) and never varied `ingestionPurpose`, so it proved nothing about the actual collision class. Replaced with a test that builds the real automatic `.activitySummary` scope twice and additionally proves the (external id, purpose) pair the Server's check actually keys on.
3. **Generic permanent-rejection churn**: for a hypothetical *non*-identity-collision permanent rejection, the fix trades "silent, zero-network permanent stall" for "one doomed upload attempt per foreground/background wake, forever" -- correctly bounded within a single call, not bounded across calls. `abandonedBatchCount` is persisted specifically so a circuit breaker could read it later, but nothing wires one up yet. Tracked as a Build 53 backlog item, not fixed here: designing a backoff policy is a genuinely separate, non-trivial piece of scope that does not belong in an already-large hotfix, and the known, confirmed collision case (the one actually observed in production) is fully resolved by the namespace fix, which breaks that specific loop on the very first retry.
4. **Server duplicate-canonical-day confidence**: the review could not inspect Server source directly and asked for confirmation beyond the `testday` precedent. I already had this from the audit phase (see "No Server change" above) -- `getHealthKitCanonicalDayRecordId(domain, localDate)` and `reconcileHealthKitCanonicalDay`'s documented behavior are direct Server-side evidence, not merely an analogy to another feature.
5. **Missing decode-backward-compatibility test**: added `testDecodingEnvelopesWithAndWithoutTheNewDiagnosticsKeysBothSucceed`, which also surfaced a real correction to my own understanding: Swift's synthesized encoder omits a `nil` Optional's key entirely (`encodeIfPresent`), it does not write `null` -- so a pre-abandonment envelope already looks exactly like a real pre-fix envelope for these three keys, with no need to manufacture one. The test proves decode succeeds both before an abandonment (keys absent) and after one (keys present with real values).

The review also gave one precise, important clarification incorporated into Step 6 below: an already-poisoned device needs **two** ordinary foregrounds to heal, not one, because the first foreground's `synchronize()` call retires the stuck partition and still reports that attempt as failed, without falling through to a fresh query in the same call.
