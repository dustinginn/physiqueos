## Part 1 — edge-case audit (read-only)

**Exact invariant:** one canonical HealthKit workout links to at most one Logger session and one Logger session to at most one canonical HealthKit workout, enforced in three layers at the deployed SHA — the domain guard `assertHealthKitWorkoutLinkAllowed` (only CONFIRMED links count; duplicate-group check), one atomic claim row per Apple workout and per Logger session (`putIfAbsent` = `INSERT … ON CONFLICT DO NOTHING`, and `put` with `expectedVersion` = `UPDATE … WHERE version = n`), and the per-owner advisory lock every command holds. A conflict never overwrites an established link; the second relationship is refused.

**Normal confirmation path for the score-99 candidate:** `confirmHealthKitWorkoutRelationship` → re-read link → `already_confirmed` short-circuit → Logger session must still be an active detailed strength session → domain guard → acquire workout claim, then session claim (each: create-if-absent; if held by another link → `LINK_ONE_TO_ONE_VIOLATION`; if released → take with `expectedVersion`, a lost race → `LINK_ONE_TO_ONE_VIOLATION`) → write link `confirmed` with `expectedVersion` → on any throw, release the claims just acquired (compensation).

**Released/restored transitions:** unlink keeps the link, workout and session and only releases claims; a system-released (`assessment_changed`) link may be restored to `candidate` by a later ingest only if no confirmed link holds its workout or its session — otherwise it stays released and never throws. Founder-owned unlinks are never undone by the system.

**Uniqueness and transaction ordering:** no schema change anywhere; uniqueness comes from the record table's primary key (claim ids are deterministic sha256 of kind+subject) and versioned updates. Ordering: lock → reads → guard → claims → link → invariants → COMMIT; every failure rolls back.

**Concurrency:** two confirmations racing for one workout or one session cannot both hold the same claim (row-atomic), and under the advisory lock they serialize anyway; a link refreshed by ingest between read and write fails the versioned `put` with a typed `409 EXPECTED_VERSION_CONFLICT` and the claims are released.

**Idempotency/replay:** an already-confirmed link returns `already_confirmed` with no writes; relink after unlink is a fresh confirmation.

**Verdict on the reviewer-noted edge case ("restore/confirm of a system-released link can throw a one-to-one violation"):** real as originally described, but **already guarded at the deployed SHA** in `refreshHealthKitWorkoutLinkCandidate` (restore stays released on collision) — it simply had **no test**. Two further gaps had no coverage either: the compensation branch when the link write itself version-conflicts, and the claim-only collision (a held claim with no visible confirmed link). **The Sep 22 candidate is exposed to, not affected by, this class**: there were no confirmed links and no claims.

**The material finding:** there was **no registered guarded execution path** to confirm a link at all — `confirmHealthKitWorkoutRelationship` had zero non-test callers, `buildHealthKitPayload` knew only policy/graduation/audit/workout-audit, and the prior reviewer had explicitly required that the confirm command be a registered operation under the advisory lock. Confirming "through the registered guarded service" therefore required building it.
