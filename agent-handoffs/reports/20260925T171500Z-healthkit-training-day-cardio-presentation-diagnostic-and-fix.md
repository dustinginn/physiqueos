## Root cause (proven)
1. **Where the rows disappear = Server, at canonical storage -> Training Day query.** `TrainingNavigationReadService.getDay` builds the day only from canonical `training` EVIDENCE OBJECTS (`listCanonicalTrainingEvidenceForDate` -> `createTrainingDayReadModel`): Logger sessions and screenshot-derived workouts. Canonical HealthKit workouts live in a separate collection (`healthKitCanonicalWorkouts`) that Training Day never read. (Native decodes/renders whatever rows the Server returns and opens each row's `href`; stages 3–6 are not where they are lost.)
2. **The Sep 21 control works because its walks are NOT HealthKit records.** Running the **actual deployed** store query + `createTrainingDayReadModel` over production data (read-only, at `e88b8ef7`) reproduced the Founder's screenshots exactly: Sep 21 = walking, walking, strength; Sep 23 = Strength only; Sep 24 = Strength only. The Sep 20–22 "Outdoor Walk" rows are screenshot-derived training evidence objects (ids like `…evidence_submission_…_images_file_N` / `Apple Health Screenshot N.jpg`, `metadata.activity_type "Outdoor Walk"`, no HealthKit reference). For Sep 23/24 no such screenshots exist — those walks exist only as canonical HealthKit workouts.
3. **The Sep 22 canary walks did NOT show a "HealthKit Cardio path" either:** the 2 canonical HealthKit walks of Sep 22 carry `coexistence.state = matches_existing_evidence_workout` (confidence 99) pointing at the two screenshot evidence workouts already on that day — they are the same physical walks. So a naive "add all canonical Cardio" fix would DOUBLE-SHOW Sep 22. The four Sep 23/24 walks have `coexistence.state = no_other_source`.
4. **Field comparison (canary vs reconciled):** canonical Cardio records are structurally identical — schema `healthkit-canonical-workout-v1`, same top-level keys, same `current` keys, `family cardio`, `canonicalType walking`, revision 1, quarantined, no link, `localDateBasis workout_start_in_workout_time_zone`. The only differences are the activation snapshot (`policyVersion` 1 vs 4) and `coexistence.state` (above). Data is valid; nothing was mutated to "satisfy a filter".

## The fix (Server only; candidate below)
- New pure module `HealthKitCardioTrainingPresentation.js` adapts a canonical HealthKit **Cardio** workout into the same evidence-shaped record the existing Training Day / session-detail code already consumes for a screenshot walk, so ordering, the day summary ("Walking · Cardio"), the row and the existing Cardio detail follow the established path with no new presentation code.
- `TrainingNavigationReadService.getDay` merges those records (date-scoped, SELECT-only store query `listHealthKitCanonicalWorkoutsForDate`; a HealthKit read failure never breaks the day and is logged as class/code only); `getSession` resolves a `healthkit_canonical_workout_…` id to the existing Cardio session detail (no exercises, no Logger session).
- **Semantics preserved:** presentation only — no Logger session/link/claim/auto-confirm, strategic eligibility stays quarantined and is never read; generic historical `walking` stays "Walking" (label comes only from the stored `canonicalType`; `indoor_walking` -> "Indoor Walk", `outdoor_walking` -> "Outdoor Walk", running/cycling analogues); Activity Day code untouched (diff contains no Activity/Progress files); Strength detail path byte-unchanged.
- **Ordering:** the established comparator sorts by the STRING `captured_at`; Logger Strength sessions store a `T12:00:00.000Z` placeholder while screenshot walks store local time with offset. The new rows use the workout's own local time with offset (e.g. `2026-09-23T06:29:52-07:00`), reproducing the Sep 21 pattern (walks, then Strength). The comparator was deliberately NOT changed (that would reorder already-accepted days). This is a finding worth knowing: Training Day ordering is by capture stamp, not workout start time (a walk after ~noon local sorts after the Strength placeholder — pre-existing behaviour for screenshot walks too).
- **Duplicate suppression (hardened after review):** a HealthKit walk is hidden only when it is an unambiguous duplicate of an ACTIVE evidence workout on the page — by the stored coexistence decision OR a live re-assessment (so a screenshot uploaded AFTER canonicalization can't double-show); ambiguous/possible/unverifiable always fail open (both shown); a superseded/retired screenshot can never make the row vanish.
- **Parity with Activity:** the adapter reuses Activity's own presentable-workout gate (new one-line export `isPresentableCanonicalCardioWorkout`), so Training Day presents exactly the Cardio workouts Activity counts (minus retired ones and on-page duplicates).
- Shared classifier: `Indoor/Outdoor Cycle` now classify as Cardio (regex `cycl(?:e|ing)`); a read-only production check found only 5 distinct existing training activity types (Outdoor Walk 124, Traditional Strength Training 87, Stair Stepper 33, Core Training 1, Indoor Walk 1) — **none is reclassified**.
