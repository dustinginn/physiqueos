# WP2-C readiness and inert recovery contract

Status: local source candidate. WP2-B and Stages 3–5 are closed PASS. WP2-C is
`WP2C_ELIGIBLE_NOT_READY`, not execution-authorized. This design does not grant
permission to publish, boot a VM, prepare live media, issue an authorization, or
use the real identity. The go-forward migration policy controls this document.

## Purpose and boundaries

WP2-C decrypts the accepted native-recipient packet offline, checks the exact ZIP
hash/length, safely extracts it, verifies the source-produced manifest and reference
index, checks restored-file hashes and credential exclusions, and leaves an inert
guest. PASS is `PHASE7B_WP2_ISOLATED_RESTORE_VERIFICATION_PASS_INERT`.
It does not start PhysiqueOS, import PostgreSQL, connect to production/provider,
change canonical authority, or authorize rehearsal/GO-B/GO-L/GO-M.

The legacy standalone restore mutation operations and authorization-embedded ISO
builder now reject execution. Their read-only compatibility readers remain for
historical provenance. The supported guest entry is
`phase7bRunWorkPackage2GuestRestore.ps1`; no caller-supplied preflight PASS replaces
its real verifier. Existing WP2-B files, markers, packets and receipts are not
rewritten or regenerated by this work.

## Provisional 1Password entry

1Password Windows supports Type in window for individual username/password fields.
Its release notes document explicit window selection; its Auto-Type guidance warns
that active-window/field mistakes can expose credentials. The vendor describes
Auto-Type as keyboard simulation rather than clipboard transfer. This is distinct
from browser autofill, generic application accessibility fill, and Copy. Sources:
[Windows release notes](https://releases.1password.com/windows/stable/),
[Auto-Type safety guidance](https://support.1password.com/windows-auto-type/),
[vendor explanation of keyboard input](https://www.1password.community/1password-at-work-58/paste-without-paste-fake-keyboard-input-24756).

This is a provisional transport into the VMware console, not a proven VMware
integration. The installed version, supported item-field type and actual guest
target behavior have not been verified. No vault/item was accessed. The exact
supported single-field action must be tested; whole-login Auto-Type, TOTP and
automatic submission are not substitutes. A secure-note/custom field must not be
assumed to support Type in window. Any custody-item change needs Founder review.

The source uses the existing native-age dialog with `GuestEntry`: two masked
TextBoxes, masked character counts, explicit Verify, Cancel, no reveal button and
no Enter/AcceptButton submission. Age format normalization and two-entry equality
remain authoritative, followed by pinned `age-keygen -y` over private redirected
stdin and exact public-recipient equality. The dialog cannot stop host-side focus
misdelivery. Founder destination selection remains a residual risk. Managed .NET
strings cannot be claimed synchronously zeroized; mutable/unmanaged buffers and
SecureStrings are cleared/disposed where supported. No identity file, environment
secret, argv secret, ConsoleHost injection, batchpass or guest vault is introduced.

## Preparation is separate from execution

Preparation GO may authorize host resource checks, exact S1-lineage inspection,
bounded tooling ISO creation, two read-only optical slots, NIC disconnection,
approved attachment/boot, narrow tooling installation, guest checks, the synthetic
entry test, shutdown and nonsecret preparation evidence. It never authorizes
packet decryption, a restore claim, a capture authorization or a restore.

Preserve the **7 GiB available host RAM** threshold: 4 GiB guest allocation plus
3 GiB host margin. Historical 4.29 GiB is not sufficient and is not a current
measurement. The host preflight also preserves the existing 120 GiB disk gate.
The Founder chooses what applications to close; no automatic process termination,
production stop, pagefile change, reboot or threshold reduction is permitted.

The retained v5 kit is not current. Install the new exact source closure into
`C:\Phase7B\isolated\tooling\<manifest-sha256>`, never over the application
repository. The installer validates guest UUID/marker, optical origin, source
closure, binaries, offline NIC, disabled task definitions, inert processes,
listener absence, NTFS capacity and clean roots before its first copy. Partial
installation remains evidence; it is not silently overwritten or retried.
Preparation establishes empty incoming, canonical restore and WP2-C state
directories; the actual extracted `packet` directory is created only in execution.
Root ACL or reparse defects stop preparation/execution rather than being repaired
by the restore entry.

Guest checks must freshly establish Windows 11 edition/build matching the reviewed
plan, licensed evaluation with at least 1,440 minutes remaining, PS 5.1 Desktop x64,
WinForms/compression availability, exact VMware Tools version/running service,
2 vCPUs and the retained 4096 MiB allocation (guest-observed usable memory allows
3584–4096 MiB for hardware reservation). Host VMX checks enforce exactly 4096 MiB.
The existing sparse 80 GiB disk is retained. No activation/internet assumption is
made. Expired/near-expired evaluation requires review, not automatic activation.

Capacity bounds are packet + 1 GiB for incoming; packet + plaintext ZIP + maximum
aggregate expanded bytes + 1 GiB for the restore volume (conservative when sharing
a volume). The tooling installer requires payload + 1 GiB. Expanded bytes are
bounded before extraction; the NoCompression capture ZIP provides a safe aggregate
upper bound no larger than its byte length. ZIP entry count is bounded at 100,000;
duplicate, traversal, forbidden and oversized entries fail. No capacity gate is
solved by deleting data automatically.

`phase7bInspectWorkPackage2CGuestPreparation.ps1` performs real read-only guest
observations after installation. `phase7bRecordWorkPackage2CPreparation.ps1`
accepts the checksum-verified, schema-checked nonsecret preparation return, not
arbitrary caller-selected report objects. It validates the actual observations
plus current powered-off host observations and Founder-reviewed synthetic entry
evidence before writing create-new evidence. The complete offline baseline/plan/
inspection/synthetic/return procedure is frozen in
[the preparation operator guide](PHASE7B_WP2C_PREPARATION_OPERATOR.md). Preparation
control is distinct from the execution control carrier below; no restore claim
or execution authorization is needed for preparation. All instructions are saved
before the RAM/boot gate; Codex need not remain open during guest operation.
Preparation binds prepared-state ID, guest identity, tooling manifest, S1 metadata,
entry-validation identity, guest observations, host observations and timestamp.
It explicitly records `wp2cExecuted=false`, `packetDecrypted=false`,
`executionClaimCreated=false`, `authorizationConsumed=false`. It does not contain
its own hash or a future execution authorization. Future preparation also creates
the empty source-owned host authorization/claim/evidence directories; missing
directories fail closed in execution tooling.

## Offline isolation

Retain NAT as the historical VM connection *type*, but require the NIC disconnected
for restore. Local optical media, age and VMware console interaction require no
guest TCP/IP connectivity. VMware Tools/console operation is not a guest network
connection. No reconnect occurs during WP2-C. Do not enable HGFS, clipboard,
drag/drop, shared folders or a secret channel. Host VMX evidence establishes
clipboard/drag/drop disablement; guest observations alone cannot prove those host
settings. Guest gates separately require no up adapter, external default route,
external established TCP connection, network drive or mapped connection.

The current VMX identity uses versioned `wp2c-semantic-vmx-v2`. It is an explicit
allowlist, not a hash of VMware's serialized file. It binds VM/guest UUID and
display identity, firmware/Secure Boot/TPM/encryption presence, CPU/RAM, the
single virtual disk/controller topology, NIC type and disconnected state,
clipboard/drag/drop/HGFS/shared-folder controls, USB restrictions and the exact
two-slot optical topology. Exactly enumerated VMware runtime/serialization fields
(for example clean-shutdown bookkeeping, NUMA/vMotion cache values and opaque
encrypted-configuration serialization) are excluded; unknown fields, duplicate
assignments and malformed lines reject. The actual phase-specific optical paths,
media hashes and effective connection states remain separately and exactly
validated. Raw stopped VMX SHA is retained as diagnostic/create-time evidence,
not used as a stable cross-save semantic identity.

Optical connection interpretation is shared by VMX projection, preparation
baseline/second-boot selection and execution boot-media checks. Only a present
SATA/IDE `cdrom-image` device with a nonempty ISO filename may use VMware's
omitted `startConnected` default TRUE. Explicit TRUE/FALSE remain distinct;
empty/null/malformed values, duplicate/invalid optical VMX assignments, absent
devices, unsupported optical types and extra slots reject. No NIC/disk default
is introduced. The narrow default follows the
[VMware employee explanation of CD/DVD startConnected omission](https://community.broadcom.com/vmware-cloud-foundation/communities/community-home/digestviewer/viewthread?CommunityKey=fb707ac3-9412-4fad-b7af-018f5da56d9f&GroupId=7171&MessageKey=e805adfb-9291-48a8-ada2-525494421e57).
The current powered-off saved representation is regression-tested without boot.
Baseline requires both optical filenames to name the exact tooling ISO and
exactly one effective connection; second boot requires tooling plus preparation
ISO and both connected. A disconnected recovery/unknown ISO is not an approved
spare. Full media hashes/bytes and all hardware/isolation gates remain mandatory.

A correction to `phase7bWorkPackage2CHost.psm1` also changes the guest tooling
closure: that module is shipped on tooling media. Existing session/media bytes
remain immutable historical preparation evidence, not current patched tooling.
After publication the original session's commit/operator bindings reject direct
reuse. The host-only preparation continuation below bridges that exact
pre-baseline state. The optical correction alone did not grant continuation.

### Pre-baseline preparation continuation

`phase7bWorkPackage2CPreparationContinuation.psm1` and the operator's explicit
`CreateContinuation` mode implement a separate, non-executable provenance bridge.
It requires a later Founder continuation GO; publication is not that GO.
The original directory is never written, renamed, deleted or rebound. Initialize
and BuildTooling are not rerun against it. Original commit/operator/ISO/manifest
remain original-lineage evidence, not current tools.

Eligibility independently pins the selected original session JSON, deterministic
recursive file inventory and current saved VMX. It validates the original exact
pre-baseline file set, all original media/content bytes, descriptor, age binaries,
VM UUID, host identity, unchanged VMSD, current S1 and preserved S0, cold state,
no suspended state, disconnected NIC and existing isolation/optical policy.
Any baseline/token, plan, accepted evidence, unexpected file, reparse or drift
rejects before creation. No RAM threshold is needed merely to create a context;
the unchanged >=7 GiB gates run immediately before EACH later boot.

The deterministic location is
`wp2c/continuations/<original-preparedStateId>/<current-published-commit>/`.
The first mutation creates that new directory without overwrite. Its replacement
`tooling-current.iso` uses the existing builder and its recorded exact guest
closure. Historical 15-file media remains immutable. Current generic tooling
media has 17 files, including the root-level `b.cmd` Baseline entry point; a
create-new baseline-handoff medium has 18, adding only the non-executable
baseline binding. The continuation module remains host-only.
Partial output is retained for
read-only reconciliation, never automatically deleted or retried.

`continuation.json` is canonical schemaVersion 1, kind
`wp2c-preparation-continuation`, classification
`PHASE7B_WP2C_PREPARATION_CONTINUATION_NONEXECUTABLE`. It binds:

- `original`: session ID/root/metadata, initialization commit/operator, complete
  inventory and its SHA, original ISO/manifest, descriptor/attempt/application/
  environment, baselineCaptured=false, planCreated=false, preparationAccepted=false.
- `current`: actual published continuation commit/operator/Host identities,
  machine-derived host dependency closure and guest tooling manifest, replacement
  ISO path/identity, manifest identity and tooling-result identity.
- `vm`: reviewed raw original VMX, original VMSD, stable optical-excluding config
  identity, guest UUID identity and S1 name; plus createdAt.
- nonExecutable=true, preparationOnly=true, automaticRetryAllowed=false,
  wp2cExecutionAuthorized=false, laterMigrationAuthorized=false.

The context is written LAST, after replacement media and rechecking original
bytes/VM pins. Canonical inventories/manifests are deterministic; creation time
and ISO filesystem metadata are recorded once, not claimed reproducible. The
current commit must be the publication containing this implementation (a
descendant of the reviewed `48af694a...` optical baseline), never falsely attributed
to a commit lacking the new operator.

Every later mode requires the exact continuation path AND SHA, current published
source/closures, untouched original inventory and current selected media. There
is no latest-context lookup or automatic migration. A compatible existing context
returns `PHASE7B_WP2C_PREPARATION_CONTINUATION_EXISTS` without writing; that is not
a retry instruction. Partial, malformed or conflicting registry entries stop.
Well-formed historical contexts of other commits do not gate eligibility by count.
Creating another context also rejects progress artifacts in a prior continuation;
it cannot restart from the frozen original after a prior baseline/plan/closeout.

All later baseline, plan, preparation media, review, return and accepted evidence
live under the continuation directory, retaining the original preparedStateId.
Only in-memory operator settings select current tooling; original session JSON
is not rewritten. Approved later optical attachment may change filenames/connection
flags, but the semantic VM projection and exact media checks still reject unsafe drift.
Both boots, synthetic test, shutdown and four-file recorder remain unchanged.
The recorder adds `preparationLineage` to preparation.json binding the exact
continuation and both original/current commits, operators, ISO and manifest
identities. It validates that lineage before any accepted-evidence write.
Guest/restore/execution schemas, claim semantics, snapshots and authority do not
change. Continuation creation grants no permission to boot, install or restore.

### Stopped-VM semantic-binding continuation

A legacy continuation may have been created with the version-1 whole parsed-VMX
projection before VMware saved an authorized optical selection. VMware may rewrite
benign runtime/serialization fields during that save, so replaying its legacy
`configSha256` can reject before the exact optical policy is reached. Never revert
approved optical paths merely to reproduce stale serialization.

`CreateVmBindingContinuation` is the single create-new host-only bridge for that
pre-baseline condition. It reads the selected parent continuation as immutable
historical provenance, requires its original inventory/media/VMSD and current
published source to remain exact, pins the current stopped raw VMX, and runs the
full semantic-v2 VM, cold/S1, NIC/integration and first-boot media gates before its
first write. It then creates
`wp2c/vm-bindings/<preparedStateId>/<currentCommit>/`, including a distinct
`tooling-semantic-current.iso`, and writes `vm-binding.json` last. The shorter
root is intentional for Windows PowerShell 5.1/.NET Framework path limits;
`parent.path` and `parent.identity` provide provenance rather than directory
nesting.

The bridge classification is
`PHASE7B_WP2C_PREPARATION_VM_BINDING_CONTINUATION_NONEXECUTABLE`. Its parent block
retains the exact legacy continuation and legacy config hash; its current block
binds the new commit/operator/Host/dependency closure/manifest/media; its VM block
binds semantic mode/hash, current stopped raw VMX, VMSD, guest identity and S1.
The same nonExecutable/preparationOnly true and automaticRetryAllowed/
wp2cExecutionAuthorized/laterMigrationAuthorized false authority flags apply.
Existing exact bridge state is reported without writes; partial, changed or
conflicting state stops without cleanup. No latest-context selection exists.

### Guest-local baseline tooling handoff

The semantic bridge remains immutable parent evidence. When its tooling predates
the guest-local Baseline launcher, `CreateBaselineHandoffContinuation` creates one
new `wp2c/baseline-handoffs/<preparedStateId>/<currentCommit>/` addendum and
distinct `tooling-baseline-current.iso`. The ISO contains the current 13-script

`wp2c-baseline-binding.json` (18 files total). The binding is nonsecret and
non-executable; it pins the accepted guest identity and independently generated
tooling-manifest hash, operation=Baseline, semantic VM identity and parent bridge.
It explicitly grants no restore, WP2-C execution or later-migration authority.

The root-level `b.cmd` is an ergonomic entry point only: after visually selecting
the `P7B_C_TOOLS` drive, the Founder types `X:\b`. It invokes System32 Windows

Baseline launcher. That authoritative guest launcher requires Windows PowerShell 5.1 Desktop x64 ConsoleHost,

and exactly one `P7B_C_TOOLS` optical volume. It validates the binding, manifest,

baseline-handoff identities separately.

Bridge-only resumed modes require exact `VmBindingPath`/`VmBindingSha256`; after a
baseline handoff they instead require exact `BaselineHandoffPath`/
`BaselineHandoffSha256`. Parent or original tooling cannot satisfy the selected
preboot gate. Accepted lineage is schema 2 for a bridge and schema 3 for a handoff,
retaining every prior provenance layer. Neither artifact boots the VM nor grants
preparation resumption or WP2-C execution.

After attachment and before boot, the host boot-permit entry independently checks
the exact two local ISO paths, full ISO hashes, optical connection flags, projected
VMX identity, S1 metadata, powered-off state, hardware and isolation. It then writes
one create-new boot permit outside the VM. It does not attach media or boot the VM.
All existing S0/S1 snapshots remain untouched by these source tools.

## Contract and authorization schemas

All WP2-C schemas are version 1, canonical JSON, UTF-8 without BOM. Current
artifact identities are `{sha256, bytes}` from source/filesystem producers, never
chat-transcribed lists. The invocation (`kind=wp2c-invocation`) binds:

- attempt, current tooling commit, application commit, environment, VM display name;
- host/guest identity hashes, VMX projection mode/hash, S1 snapshot metadata/name,
  prepared-state ID and preparation-evidence hash;
- final descriptor, ciphertext, plaintext ZIP, maximum expanded bytes, media
  descriptor, recovery ISO, tooling ISO and tooling manifest identities;
- exact native public recipient/mode, age/keygen 1.3.1 hashes/bytes, prepared Git
  binary identity, guest marker/name/OS/Tools version, source-owned local roots;
- provisional entry method and accepted synthetic evidence hash, disconnected
  network policy, claim/completion schema versions;
- guest and host actual transitive source closures, including entry, verifier,
  contracts, native bridge, media, authorization, claim, boot-permit and closeout.

The invocation has no timestamp/randomness and regenerates byte-identically from
the same source and explicit inputs. It includes source hashes, not its own hash.
Authorization and host claim/boot/closeout paths additionally require the exact
branch, HEAD, matching local origin reference and clean tracked/untracked tree.
Non-executable local generator tests may use a development tree; that cannot grant
execution authority. The publication/Founder GO review must separately recheck the
actual remote, since the source guard intentionally does not perform a network fetch.
Preparation/observation plans are non-executable inputs; final binding validation
and execution re-observation are mandatory. No caller-supplied success flag grants
authority. A private identity prefix in bindings is rejected.

Authorization (`kind=wp2c-authorization`) contains a generated ID, exact invocation
hash and complete bindings, stage `WP2C_ISOLATED_RESTORE`, issue/expiry timestamps,
24-hour maximum lifetime, `oneUse=true`, `mutationBudget=1`,
`automaticRetryAllowed=false`, `wp2cAuthorized=true`, `laterMigrationAuthorized=false`.
Selection always includes exact file path/hash. Strict boolean types, current
bindings and lifetime are checked. Historical counts never gate eligibility.
Older-commit artifacts remain audit evidence; an eligible or malformed current
candidate blocks creation. Creation is serialized with an exclusive nonsecret
coordination file. Claimed/completed current work requires reconciliation, not
automatic replacement or deletion.

## Durable one-shot state

Host ledger: `C:\Phase7B\host-evidence\379bb303\wp2c\claims`, outside guest disks,
snapshots and shared folders. Guest ledger: the bound `wp2c-state` directory.
Create-new/FileShare.None plus `Flush(true)` writes claims and completion records.
A partial/corrupt existing record still blocks reuse. Claims are never auto-cleared.

Host claim binds authorization ID/hash, invocation, complete binding hash, claim
ID, side and time. The later create-new `.boot.json` binds the claim, invocation,
exact recovery/control media and observed raw VMX. The host path rejects an existing
claim/completion; the boot-permit path rejects a repeated permit. No source tool in
this candidate powers on, reverts, suspends, snapshots or edits the real VM.

The guest requires the hash-bound host claim and the independently supplied host
boot-permit hash. It verifies control/media/preparation, performs real preflight,
collects/verifies the identity, repeats preflight and expiry checks, then creates
its claim before staging. The host claim is already spent even if guest identity
entry cancels. Guest completion binds guest claim and PASS-evidence hash. Host
closeout requires the actual external host claim/boot permit and matching guest
evidence/completion; it writes a separate terminal host completion.

A guest rollback cannot remove the external host ledger or restore authority in
the supported host launch/closeout workflow. **Offline limitation:** a copied
read-only carrier is not a cryptographic monotonic counter inside a reverted VM.
The guest cannot independently query the disconnected host ledger. Direct manual
VM rollback/boot or reuse of an old carrier bypasses the supported host workflow
and is prohibited, not claimed physically impossible. Never authorize a bare
guest-only retry. A fresh real identity entry is still required after cold rollback;
no secret-bearing memory snapshot is allowed. This limitation must be visible in
future Founder review, not hidden behind a replay-proof claim.

## Mandatory pre-mutation ordering

The guest entry verifies current contract/auth/media/descriptor, real VMware
manufacturer/model and exact UUID/name/marker; exact application repository HEAD
and clean state; exact installed tooling/file set/binaries; expected OS/evaluation,
PS/.NET/Tools/hardware; task definitions disabled and controls stopped; no node,
ngrok, database process or port-3000 listener; credential file/environment exclusions;
local NTFS roots, ACL ownership, no reparse escape, capacity and clean destinations;
HGFS/share/network absence. Host preparation and boot evidence cover host-only
integration/snapshot/VMX assertions.

Only then does the masked UI collect the identity. `age-keygen -y` receives it on
redirected stdin and must derive the bound recipient. Repeat real gate and expiry
after UI, create guest claim, copy exact ciphertext, decrypt with `age --decrypt
-i -` using retained in-memory identity, dispose identity, hash/count the temporary
ZIP against banked WP2-B identity, bound/extract it, verify all restored files and
reference index, repeat inertness checks, remove only the owned temporary ZIP,
write create-new PASS evidence, and write completion. No application/database starts.

## PASS, return and snapshot closeout

PASS evidence binds authorization, host claim/boot permit, guest claim, invocation,
full bindings/preparation/media identities, native recipient, guest/VM/application,
age/keygen, exact ciphertext and ZIP identity, restored root/count, source inventory,
reference index and manifest/file/credential verification, runtime/network inertness,
ZIP removal, timestamp and no-retry/no-later-authority flags. It explicitly leaves
`s2Created=false` and `hostCloseoutComplete=false`. Completion is a separate durable
record containing authorization ID, claim SHA, evidence SHA and completion time.

The guest emits the complete nonsecret evidence and completion objects plus their
canonical hashes. With integrations disabled, the minimum return mechanism is
Founder-reviewed console transcription/screenshots of **nonsecret data only**.
The source importer canonicalizes and checksum-verifies both objects and validates
their bindings before create-new host persistence. It never executes pasted code.
Truncated or mistranscribed data fails; do not invent missing fields/hashes. This
can require several console captures; it is intentionally not a new guest network,
clipboard or secret channel. Any more convenient return transport needs separate
review. Host completion consumes no WP2-B authorization.

Start from S1 lineage, preserving S0/S1. Preparation is banked by a new prepared-state
ID/evidence, not by overwriting S1 or taking a memory snapshot. Execution starts
only from that exact installed prepared state. Guest PASS, host completion, cold
shutdown and S2 creation are distinct facts. S2 is the accepted inert restored
guest **after shutdown**, under separately defined closeout authority. A failed
shutdown/S2 operation cannot justify replay or decryption. Preserve S2 for later
