# Combined App Platform and persistence cutover

Status: implementation and isolated rehearsal design only. This document is not a production migration authorization. Windows, legacy JSON, and local production media remain authoritative until a new, exact combined-cutover authorization is issued.

## Why the transition is combined

A persistence-only transition cannot complete while the accepted PostgreSQL firewall permits only App Platform and the Windows serving runtime cannot consume the new canonical store. Moving the full application first also cannot complete because App Platform's ephemeral filesystem cannot provide the shared, durable semantics required by the legacy JSON and media implementation. A bridge or a temporary durable legacy store would create another authority plane and an immediate second migration.

The selected transition therefore moves serving, commands, reads, domain persistence, media, migration control, worker, and outbox authority together:

`Windows Next.js + legacy JSON/media -> fenced combined cutover -> App Platform Next.js/worker + PostgreSQL/Spaces`

The web product remains a first-class client. A future iOS client will call the same versioned application/API boundary. Neither client owns canonical storage; both observe PostgreSQL and private Spaces through the shared server application layer.

## Authority map

| Concern | Before the cutover | After accepted cutover |
| --- | --- | --- |
| Web serving and public routing | Windows production task and its current route | App Platform full Next.js web service and provider route |
| Canonical commands and reads | Windows application over Founder JSON | App Platform application boundary over PostgreSQL |
| Founder runtime | Versioned legacy JSON on Windows | PostgreSQL canonical tables and runtime metadata |
| Production media | Windows local evidence tree | Private, versioned Spaces objects plus PostgreSQL ownership records |
| Migration/runtime control | Protected Windows control and runtime-authority record | Transactional PostgreSQL control and runtime-authority record |
| Worker and outbox | Existing Windows-owned behavior; provider worker inert for production | One authority-gated App Platform worker and PostgreSQL outbox |
| Operational control | Windows task and protected local operations | App Platform health/readiness/operations with strong server-side authorization |
| Recovery | Current Windows build, JSON/media, and encrypted packet | Provider-compatible code rollback, PostgreSQL recovery/forward repair, Spaces versions; retained Windows data is recovery evidence only |

No intermediate phase has two canonical writers. PostgreSQL and Spaces may contain validated noncanonical copies before authority transfer, but those copies do not become canonical merely by existing.

## Machine-checkable invariants

The durable runtime-authority tuple binds environment, operation ID, authorization fingerprint, fence ID, final snapshot digest, Founder revision/digest, media manifest digest, migration-control digest, Windows source/build, provider source/build/deployment, PostgreSQL target, Spaces target, and routing target.

- `windows-legacy-authoritative` is the only state in which Windows may accept canonical writes.
- `combined-cutover-in-progress` requires an active matching Windows fence. No application accepts canonical writes.
- `provider-prepared` requires exact transfer receipts, PostgreSQL/Spaces semantic parity, provider readiness, and matching control/worker acknowledgements. It is non-public and write-blocked except for explicitly synthetic acceptance.
- `provider-authoritative` is entered once for the exact tuple. Windows can never regain write authority from this state.
- `recovery-required` preserves provider/PostgreSQL authority while writes may be paused for compatible-code rollback and forward repair.
- A provider canonical command must atomically verify `provider-authoritative` and record the first-provider-write marker in the same PostgreSQL transaction as its canonical mutation.
- A Windows command must fail closed whenever its protected control is fenced or no longer Windows-authoritative.
- A provider upload is noncanonical until private object readback validation and the final PostgreSQL ownership transaction succeed. Failure aborts multipart upload or deletes the exact uploaded version.
- The worker polls only when the same provider-authoritative tuple is complete; leases, retries, dedupe keys, and terminal receipts remain PostgreSQL-durable.
- No runtime falls back to Founder JSON, local media, or ephemeral container disk in provider canonical mode.

## Production phase model

1. **A — pre-fence validation.** Re-read live source/build, Founder revision and SHA-256, media inventory, control digest, targets, firewall, backups, provider compatibility deployment, routing preparation, capacity, alerts, and exact new authorization. Abort without mutation on drift.
2. **B — Windows fence.** Activate the protected Windows write fence for the exact operation. Reads follow the maintenance contract; all canonical commands and upload completion are rejected. Drain in-flight work and prove the fence across Workout Logger, evidence, weight/check-in, priorities, goals/protocols, and uploads.
3. **C/D — final capture/package.** After the drain, capture one authoritative JSON/media/control snapshot and create one deterministic package-v2 identity. Re-read the source after capture to prove it did not change behind the fence.
4. **E — one-time transfer.** Transfer only the authorized package and its declared media manifest over TLS to the provider execution boundary. Chunks are scoped to operation, artifact, ordinal, byte range, size, and SHA-256. Replays are idempotent only when bytes and metadata match; drift is rejected. The final receipt binds the complete manifest and authorization fingerprint. This is a cutover operation, not a continuing synchronization service.
5. **F/G — non-public import.** Import domain state transactionally into the exact PostgreSQL target and copy media privately into versioned Spaces. Objects remain noncanonical until manifests, ownership, MIME, length, hash, and version IDs validate.
6. **H/I/J — provider validation.** Validate complete semantic read parity, command readiness without legacy writes, media reads/uploads, full product route inventory, health, readiness, worker/outbox, and source/build identity while provider public writes remain disabled.
7. **K — durable preparation.** Record exact transfer receipts and provider/control/worker readiness. Both sides must show the same tuple. Windows records the provider acknowledgement while retaining its fence.
8. **L — authority/routing handoff.** Atomically transition provider runtime authority, keep Windows fenced, enable the prepared App Platform route, and verify that only the provider can reach the canonical command boundary. Routing must not lead this step.
9. **M — combined first-write boundary.** The first real canonical production command accepted through the provider application is committed with the first-write marker. This is the irreversible boundary.
10. **N/O — release and smoke.** Release writes only through the provider platform, start the authority-gated worker, and perform immediate web/read/write/media/user-facing acceptance. Windows remains stopped or read-only and cannot accept writes.
11. **P — stabilization.** Enter the approved observation period, reconcile domain/media/outbox state, verify backups and cross-client semantics, and retain legacy recovery material for at least the approved 35 days and until every exit condition passes.

## Fence and final snapshot ownership

Windows owns the fence through final snapshot capture and provider-prepared acknowledgement. The fence denies every canonical command, including logger finish, evidence confirmation, weight/check-in, priority completion, goal/protocol edits, and upload completion. Reads may continue from the frozen legacy snapshot with an explicit maintenance status. Provider control does not become authoritative at import time; it becomes authoritative only during the single authority transition after exact preparation evidence exists.

## One-time authenticated transfer

The transfer initiator supplies an operations-authenticated request whose digest is bound into the separately approved authorization. The provider verifies a short-lived credential using the existing server-only credential pepper, requires the exact operation and deployment identity, and permits only declared package/media artifacts. TLS is mandatory. The receiver stores chunks in noncanonical temporary storage, verifies each SHA-256, records idempotent PostgreSQL receipts, and assembles only after every declared range exists. It verifies package, Founder, media, control, source/build, target, and authorization digests before acknowledging `provider-prepared`.

The interface never accepts arbitrary destination paths, shell commands, bucket keys, or caller-selected database objects. Raw Windows paths and provider object keys never appear in client responses. Interrupted upload resumes by asking for missing declared chunks. A mismatched replay, extra artifact, expired credential, cross-owner request, or tuple drift fails closed. Temporary artifacts are removed after completion/abort under the approved retention rules.

Pre-staging may contain only synthetic or explicitly nonauthoritative data. The final authoritative package is created and transferred only after the fence.

## PostgreSQL and application composition

Provider full-runtime mode composes all Founder repositories from PostgreSQL. Reads hydrate a fresh canonical runtime. Mutations execute under a PostgreSQL advisory lock and transaction, compare the expected full-runtime fingerprint, apply the application unit of work, persist all changed canonical collections/context/metadata, record provenance and outbox effects, and advance runtime revision. Compatibility mode is restricted to named isolated test databases and can never claim production authority.

Server components, actions, and `/api/v1` share application handlers. Provider mode has fail-closed build replacements for Founder file runtime and protected Windows migration control. There is no JSON fallback or dual write. The same command contracts—idempotency, expected versions, ownership, provenance, replay/drift rejection, suppression, and outbox—apply independently of whether the caller is web or future iOS.

## Media and domain atomicity

New provider uploads use a durable intent and private multipart upload. The server validates declared type/length/hash, performs private readback validation, then commits ownership, canonical media metadata, related record mutation, first-write claim when applicable, and outbox entry in PostgreSQL. A failed upload is aborted; a failed final transaction compensates by deleting the exact object version. Retry is keyed to the intent and identical payload; payload drift is rejected.

Existing migrated objects are accepted only when the final inventory validates count, bytes, MIME, SHA-256, owner, logical media ID, object version, and no public ACL. Clients see `media://` logical references and short opaque application handles. The server redeems them, rechecks owner/expiry, and proxies a signed private read without revealing object keys.

Canonical private-media object IDs are opaque values in either the current migrated form `media-<32 lowercase hex>-<12 lowercase hex>` or the retained UUID form used by provider uploads and legacy records. A provider-backed boot acceptance exposed an obsolete UUID-only check in the private-evidence route; the route and directly related media-reference consumers now use the shared identifier contract. This additive alignment does not accept storage keys or paths: traversal encodings, separators, URLs, control characters, extra route segments, and malformed or overlong values remain rejected before owner-scoped lookup, while ownership and opaque-handle redemption remain mandatory authorization steps.

## Worker handoff

The Windows/background producer is drained before final capture. The provider worker may run in compatibility mode but cannot poll the production outbox until the exact authority tuple is provider-authoritative. Authority-gated polling, durable leases, idempotent handlers, retry/dead-letter rules, and dedupe prevent duplicate canonical effects. The first provider worker heartbeat and outbox health are readiness requirements. Failure after handoff pauses work or enters `recovery-required`; it never restarts a stale Windows consumer.

## Routing handoff

The current Windows public route and any LAN/tunnel fallback remain unchanged in this patch. Before the future window, the exact provider hostname, TLS, rollback mechanics, TTL/dashboard action, and operator are recorded. The route is prepared but not enabled until provider preparation is durable. Windows stays fenced throughout the switch. A pre-first-write routing failure may return traffic to the unchanged fenced/then-unfenced Windows snapshot after the abort verifier passes. After the first provider write, traffic may move only among schema-compatible provider builds; it never returns to a write-enabled stale Windows runtime.

## Rollback and recovery matrix

| Point | Permitted response |
| --- | --- |
| Before fence | Abort; Windows remains authoritative and writable. |
| Fence through provider-prepared, before authority transfer | Remove noncanonical provider artifacts as allowed, verify the Windows snapshot/control are unchanged, release the exact fence, and resume Windows. |
| Authority transferred but no provider canonical write | If exact invariant checks prove no provider write, reverse routing/control once, restore Windows legacy authority, then release its fence. Any uncertainty fails closed. |
| First provider canonical write recorded | PostgreSQL/Spaces and App Platform remain canonical. Pause writes, promote a schema-compatible provider rollback build/spec, and repair/reconcile forward. Windows remains write-disabled. |
| Media completion partially fails | Abort/delete exact noncanonical version or reconcile the durable intent/outbox; never leave an accepted record permanently pointing to missing media. |

Synthetic rehearsal injects failures at fence, snapshot, transfer, import, media, database validation, Spaces validation, read parity, command readiness, routing preparation, acknowledgement, first provider write, media finalization, and worker startup. Pre-boundary cases must restore an unchanged legacy fingerprint; post-boundary cases must enter `recovery-required` with provider authority preserved.

## Implementation Phase 1 — cutover authority initialization (2026-08-18)

The Founder approved this document as the target production cutover architecture. Phase 1 begins its production wiring and is limited to durable authority-record preparation.

## Implementation Phase 3 — authenticated provider transfer service (2026-08-18)

Phase 3 implements the production authenticated transfer channel behind the synthetic `transferSnapshot` contract that Phase 2B proved (`src/platform/cutover/syntheticCombinedCutoverRehearsal.js`), and the real Windows-side adapter that drives it. It is limited to transfer plumbing: no public routing handoff, no real worker handoff, no provider deployment, and no complete production adapter set. Transfer alone never imports canonical data, transfers runtime authority, sets `firstProviderCanonicalWriteAt`, enables provider production writes, or switches routing — every module in `src/platform/cutover/transfer/` is statically proven (`CombinedCutoverTransferAuthorityIsolation.test.js`) to import nothing from the runtime-authority state machine, the authority store, the canonical record store, or the worker.

**Two layers, two receipt tables, deliberately not merged.** The existing `physiqueos.combined_transfer_receipts` (migration 000005, previously unused by any HTTP surface) is reused unchanged as the OPERATION-level manifest declaration and final cross-checked completion: one row per `migrationOperationId`, bound to `packageDigest`/`runtimeSha256`/`mediaInventorySha256`/`migrationControlSha256`, idempotent on an identical redeclare, rejecting drift. A new, additive migration `000006_combined_cutover_transfer_staging.cjs` adds `physiqueos.combined_cutover_transfer_receipts` and `physiqueos.combined_cutover_transfer_chunks` for the BYTE-level, chunked, resumable transfer of each individual package artifact (`manifest.json`, `canonical-runtime.json`, and every media file — each identified by an opaque `packageId` derived from its package-relative path, never by a raw path). The two tables model different facts with different lifetimes — "this operation is authorized to transfer this package" versus "3 of 41 chunks of media file 7 have landed" — so they are not overloaded into one schema.

**Chunking and size.** A realistic production package (Founder runtime revision 140, 30,262,748 bytes, plus 402 media files / 288,919,315 bytes) is far larger than is safe to assume as one HTTP request through the App Platform proxy into a 512 MiB instance, so transfer is chunked and resumable by construction (default 8 MiB, capped at 16 MiB per chunk). Every chunk is bound to `(operationId, packageId, overallDigest, chunkIndex, chunkDigest, expectedChunkCount, expectedBytes)`. The server independently recomputes each chunk's SHA-256 from the bytes it actually received and rejects any mismatch; a chunk's declared Content-Length is checked before the body is buffered.

**Authentication is separate from the Founder access gate.** `combinedCutoverTransferAuth.js` verifies a short-lived, operation-bound machine credential using the existing server-only credential pepper and `hashHighEntropyCredential`/`verifyHighEntropyCredential` (`src/platform/auth/credentialHash.js`) — the same primitive the Founder gate's session tokens do not use but that this transfer channel does, reusing an existing pattern rather than inventing a new one. Only the credential's HMAC is ever held by the provider; the plaintext exists only in the Windows client's environment. The credential is scoped to exactly one `migrationOperationId`, carries an explicit `PHYSIQUEOS_COMBINED_CUTOVER_TRANSFER_CREDENTIAL_EXPIRES_AT`, is revocable by clearing or rotating one environment value, and authorizes byte transfer only. Missing or malformed configuration disables the whole channel (`TRANSFER_NOT_CONFIGURED`) rather than degrading to unauthenticated. Because the transfer routes (`/api/v1/operations/combined-cutover/transfer/**`) are machine-to-machine, they are exempted from the Founder session-cookie gate in `src/platform/accessGate/publicRoutes.js` — deliberately, not by omission — while remaining fully protected by this separate, fail-closed machine authentication underneath. Authentication never substitutes for operation/package/digest validation: every authenticated request is still fully validated by the receipt stores.

**Staging substrate.** Received chunk bytes are non-authoritative and are staged in the existing private, versioned Space rather than the App Platform container filesystem, which the compatibility-remediation history in this document already established is ephemeral and unsuitable for durable evidence. Staged objects live under a dedicated `cutover-transfer/<operationId>/<packageId>/chunks/<ordinal>` namespace, wholly disjoint from canonical Founder media's `private/<ownerUserId>/<objectId>/` namespace (`SpacesPrivateObjectProvider.js`'s `createPrivateObjectKey`). Keys are constructed server-side only from already-validated opaque identifiers and are re-checked against a whole-string pattern before every object operation, so no traversal, separator, or namespace escape is possible and the Windows client is never handed a bucket key, a signed URL, or any canonical-media write capability.

**Independent verification, never client-asserted.** A byte-level artifact is marked `verified` only after the provider assembles every received chunk from staging in order and independently recomputes the whole-artifact SHA-256 — a mismatch marks the receipt `failed`, never `verified`. The operation-level manifest is marked `verified` only after the provider mechanically cross-checks every declared file's own already-verified byte-level receipt against the manifest's declared digest and byte length; the client never submits a verification result, only an operation identity.

**Idempotency and resume.** Declaring the same `(operationId, packageId)` twice with identical geometry is a no-op idempotent replay; a differing digest, size, or chunk count fails closed (`TRANSFER_PACKAGE_DIGEST_CONFLICT` / `TRANSFER_PACKAGE_SIZE_CONFLICT` / `TRANSFER_CHUNK_COUNT_CONFLICT`). Re-uploading an identical chunk is always a safe idempotent replay verified by digest, not merely presence; a conflicting chunk at the same index fails closed (`TRANSFER_CHUNK_CONFLICT`). One operation's credential can never act on another operation's transfer (`TRANSFER_OPERATION_FORBIDDEN`), and status reads are scoped strictly to the caller's own `(operationId, packageId)`. The Windows adapter's resume strategy is deliberately simple rather than bandwidth-optimal: on resume it redeclares (idempotent) and re-sends every chunk, relying on cheap idempotent replay for already-received chunks rather than tracking exactly which indices landed — correct and resumable, with bandwidth-efficient resume left as later work.

**Durable receipts.** The byte-level receipt (`combined_cutover_transfer_receipts`) carries `schemaVersion`, `receiptId`, `operationId`, `packageId`, `overallDigest`, `expectedBytes`, `receivedBytes`, `expectedChunkCount`, `receivedChunkCount`, `status`, `createdAt`, `updatedAt`, `completedAt`, `verifiedAt` — never payload bytes. Neither receipt table nor any response projection (`publicReceipt`/`publicManifestReceipt`) ever echoes staged bytes, staging keys, Windows paths, Spaces keys, or credentials.

**Windows-side adapter.** `WindowsCombinedCutoverTransferClient.js` implements `createCombinedCutoverTransferHttpClient` (HTTPS-only, bearer machine credential, bounded retry) and `createProductionTransferSnapshotAdapter`, which preserves the synthetic rehearsal's `async ({ input, state, snapshot, exported }) => receipt` interface exactly, so it can be substituted into `CombinedAppPlatformCutoverOrchestrator` without changing the orchestrator. It refuses to transfer if the exported package's digest does not match the fenced snapshot already bound into runtime authority by `BEGIN_CUTOVER`. Automatic retry is bounded and applies only to network-level failures and the small set of explicitly retryable codes (`TRANSFER_STAGING_UNAVAILABLE`, `TRANSFER_TRANSPORT_FAILED`); every semantic rejection — authentication, operation binding, digest/size/count conflict, chunk conflict — is raised immediately, never retried.

**What remains blocked after Phase 3.** Real public routing handoff, real provider worker handoff, real provider deployment of the product image, `importProviderCanonicalState` (real canonical PostgreSQL/Spaces import), real `verifyProviderParity`/`acknowledgeProviderPrepared`/`transferAuthorityAndRoute`/`verifyPostHandoff` adapters, and combined-cutover recovery evidence capture. Production cutover remains blocked until those exist and a full rehearsal passes against them under this transfer service. The prior migration GO remains permanently invalid; nothing in Phase 3 authorizes deployment, a Trusted Source, a DigitalOcean PAT, a production fence, provider authority transfer, a routing switch, stopping Windows, or Founder GO.

Parity already `passed` returns immediately. Acknowledgement already `acknowledged` returns the same deterministic acknowledgement object. ## Implementation Phase 5 — authority/routing handoff (2026-08-19)

Phase 5 converts `transferAuthorityAndRoute` (phase L: "Atomically transition provider runtime authority, keep Windows fenced, enable the prepared App Platform route, and verify that only the provider can reach the canonical command boundary. Routing must not lead this step.") to a production-capable implementation. It stops at that boundary: `verifyPostHandoff` gets only the narrow return shape a future implementation needs to consume, and `restoreWindowsAuthority`/`enterProviderRecovery`/the six preflights/Windows fence-snapshot-export wiring remain synthetic, as does real worker start (see below for why that is correct, not deferred).

**Authority commits before routing, never the reverse - and distributed atomicity is never claimed.** `ProductionAuthorityHandoffService.js` (`src/platform/cutover/handoff/`) never writes `combined_runtime_authority` directly and never calls `claimCanonicalWriteBoundary`. It calls the orchestrator-supplied `commitAuthority` closure - already wired by `CombinedAppPlatformCutoverOrchestrator.js` to `authorityStore.transition(TRANSFER_TO_PROVIDER, ...)`, i.e. the real `applyCombinedRuntimeAuthorityTransition`/`PostgresCombinedRuntimeAuthorityStore` - and only decides *when* it is safe to call it. Durable PostgreSQL authority state and external routing (DigitalOcean, DNS, a tunnel) cannot be committed as one distributed transaction; this module states that plainly rather than pretending otherwise, and sequences accordingly: authority commits first and durably, then routing activates, then routing is verified. `firstProviderCanonicalWriteAt` is never touched here and remains null immediately after a successful handoff; the first real authority-protected provider canonical command remains a wholly separate, later action, proven by an integration test that afterward calls the real `claimCanonicalWriteBoundary` and shows it - not this adapter - is what sets the boundary.

**The central invariant, checked independently from durable state on every call, before any mutation.** Authority must be exactly `provider-prepared`; the same operation/authorization-fingerprint/fence/package-digest tuple must match, cross-checked against both the live authority row and the acknowledgement object; `firstProviderCanonicalWriteAt` must be null; Windows must still hold public routing and writes must still be disabled; and durable Phase 4 preparation evidence must show `preparedStatus='acknowledged'` for the exact package digest. None of this trusts the orchestrator's in-memory `state`/`acknowledgement` alone - every check re-reads durable state, so a provider process restart between acknowledgement and handoff changes nothing about what this module can determine.

**Worker handoff is deliberately not this adapter's responsibility.** The synthetic Phase 2B rehearsal adapter folds a worker-handoff step into the same call for rehearsal simplicity, but this document's own phase model places "start the authority-gated worker" at phase N/O - strictly after the first-write boundary (phase M), a later, distinct phase from authority/routing handoff (phase L). Source analysis, not assumption, is what determined this module touches no worker state at all; `CombinedCutoverHandoffAuthorityIsolation.test.js` proves it statically.

**Routing-control contract: four operations, deliberately not more.** `src/platform/cutover/routing/combinedCutoverRoutingControl.js` defines `inspectCurrentRoute`, `activateProviderRoute`, `verifyProviderRoute`, and `restoreWindowsRoute`. Route *preparation* (hostname, TLS, rollback mechanics, operator) is a separate, earlier, out-of-scope readiness concern - one of the six preflights (phase A) - so there is no `prepareProviderRoute` here. `createUnavailableRoutingControl` is the fail-closed production default: every operation throws `ROUTING_CONTROL_UNAVAILABLE` rather than silently no-op-ing or synthetically succeeding, because real routing cannot be truthfully exercised without a provider-backed compatibility deployment. With this default wired in, authority still genuinely commits (a real, currently-exercisable capability); only the routing step fails, honestly, and the orchestrator's existing recovery path safely restores Windows because no write ever landed. `createDeterministicCombinedCutoverRoutingControl` (test-support only) is the in-memory double used by unit and integration tests to exercise every real branch - including ones the permanently-unavailable default can never reach - without any live DigitalOcean call. **No real DigitalOcean routing implementation was added in Phase 5; it was intentionally deferred**, as instructed, because it cannot be truthfully exercised without a provider-backed compatibility deployment - but the contract is structured so a real implementation plugs in later without touching authority semantics at all.

**No HTTP endpoint triggers the handoff itself.** The orchestrator's `commitAuthority` closure is a live JS reference that cannot cross a network boundary, so the real transition can only run in-process wherever the orchestrator itself runs. Building an HTTP surface for it would therefore be either useless (nothing could actually invoke `commitAuthority` remotely) or would require bypassing it (directly mutating authority - explicitly forbidden). Following the instruction to prefer the narrowest surface with genuine value rather than build an API "solely because previous phases used one," Phase 5 adds exactly one authenticated, READ-ONLY status endpoint (`GET /api/v1/operations/combined-cutover/handoff/status`) for cross-process recovery diagnosis, gated by a third, distinct machine credential (`combinedCutoverHandoffAuth.js`, `PHYSIQUEOS_COMBINED_CUTOVER_HANDOFF_*`) - narrower and more sensitive than the Phase 3 transfer or Phase 4 preparation credentials, since authority transfer is the single most consequential capability in the whole cutover. Unlike the prior two credentials, this one also binds to an explicit environment, and the composition additionally refuses to activate under `PHYSIQUEOS_PROVIDER_COMPATIBILITY_MODE=1` - a compatibility runtime must never observe real authority-handoff evidence even read-only.

**Durable handoff evidence: a new, narrow, additive table, not a second authority state machine.** Migration `000008_combined_cutover_handoff_receipts.cjs` adds one operation-bound `combined_cutover_handoff_receipts` row covering: the expected route snapshot before handoff, the intended routing target and provider deployment identity, whether authority committed (and to what resulting authority) and when, and whether routing activated, verified, or failed and when. `physiqueos.combined_runtime_authority` remains the sole authority source and the sole `firstProviderCanonicalWriteAt` source; this table is diagnostic/recovery evidence only, evaluated separately from Phase 4's `combined_cutover_preparation_receipts` because preparation's own semantics end at "provider-prepared," a phase before this one. No payload contents, no secrets.

**Idempotency.** A durable receipt already showing authority committed AND routing verified short-circuits immediately with zero further routing calls of any kind. A partially-completed receipt (authority committed, routing pending/failed) resumes exactly where it left off - re-reading the durable authority state instead of re-invoking `commitAuthority` needlessly, since a second `TRANSFER_TO_PROVIDER` call would in any case be safe via the orchestrator's own command-ID replay, but re-reading avoids depending on that as the only safety net. A conflicting operation (different package digest, routing target, or provider deployment for the same operation ID) fails closed at `handoffReceiptStore.declare`.

**Crash/recovery behavior, proven by an integration test for each case.** Before `TRANSFER_TO_PROVIDER`, every precondition failure (wrong authority state, wrong operation, wrong public-runtime state, unmet preparation evidence) is rejected before any authority mutation - proven directly against the real state machine. If routing activation fails outright after authority commits, `firstProviderCanonicalWriteAt` is still null, so `ABORT_TO_WINDOWS` remains legal per `CombinedRuntimeAuthorityState`'s own guard (it accepts `provider-authoritative` as long as no write landed), and the orchestrator's *existing* recovery path safely restores Windows - proven end to end through the real orchestrator, not simulated. If routing *verification* fails after activation succeeded, the durable evidence is never downgraded to "failed" (routing may genuinely be live); it stays "activated," an honestly-ambiguous state left for a later `restoreWindowsAuthority` (out of scope here) to resolve deliberately. After the first real provider canonical write, `ABORT_TO_WINDOWS` is rejected by the real state machine's own guard - proven directly, not asserted.

**No dual authority, proven structurally.** An integration test walks the full committed audit trail and asserts no row ever shows `writesEnabled=true` with `publicRuntimeAuthority` and `migrationControlAuthority` disagreeing; `CombinedRuntimeAuthorityState`'s own validator already enforces this per-state, and the audit trail proves it held at every recorded transition of a real run.

**What remains blocked after Phase 5.** A real DigitalOcean-backed routing implementation (deferred - cannot be truthfully exercised without a provider-backed compatibility deployment), real public routing, real provider worker handoff (a separate, later documented phase per this document's own model), real provider deployment of the product image, `verifyPostHandoff`, `restoreWindowsAuthority`, `enterProviderRecovery`, and the six preflights. Production cutover remains blocked until those exist and a full rehearsal passes against them. ## Phase 7B provider-control foundation — checkpoint 3 (2026-08-20)

Checkpoint 3 adds the narrow production DigitalOcean HTTP foundation under `src/platform/provider/digitalocean/`; it does not implement routing control, worker control, authority transitions, or the external A-P coordinator. The client exposes explicit app read/full-spec update, exact deployment read/create, exact action read, and domain/domain-record read and CRUD primitives. App updates preserve the caller-rendered full specification unchanged inside DigitalOcean's documented `{ spec, update_all_source_versions }` request envelope; the transport never merges provider specs or chooses intended routing state.

**Mutation ambiguity is a hard boundary.** Every request has a finite deadline and bounded response body. GET retries default to zero (an injected configuration may allow at most three attempts for transport failures only). POST/PUT/DELETE always make exactly one transport attempt: an HTTP rejection is conclusively `PROVIDER_REQUEST_REJECTED`, while a timeout, reset, truncated/malformed successful response, unexpected content type, or oversized successful response is `PROVIDER_MUTATION_AMBIGUOUS`. The client never automatically retries a mutation. The separate in-process reconciler permits bounded readback with a caller-owned expected-state predicate and classifies the result `PROVEN_APPLIED`, `PROVEN_NOT_APPLIED`, or `STILL_AMBIGUOUS`; a still-ambiguous resource remains guarded against a second mutation until the same operation resolves through read-only reconciliation. This guard is explicitly not distributed locking—the future coordinator must durably serialize operations across processes.

**Exact identity and evidence.** Provider resource/deployment/action identity is distinct from the caller's local operation/command identity; the latter is evidence for coordinator correlation only and is not represented as a DigitalOcean idempotency guarantee. Polling has a finite interval/deadline, reads only the exact returned deployment/action identity, recognizes explicit pending/success/failure state sets, and fails closed on wrong identity or unknown state. Safe evidence contains only method, resource kind, path template, status, timing, timeout/retry count, rate-limit metadata, operation identity, and provider IDs. Central redaction removes authorization data, PAT/OAuth-token patterns, credentials/hashes, signed-URL query values, and other sensitive query parameters; arbitrary provider error bodies and full specs are never copied into errors or evidence.

**Least privilege and execution boundary.** The documented app capability set is `app:update`, `app:read`, `regions:read`, `sizes:read`, and `actions:read`; DNS uses only the applicable `domain:read`/`domain:create`/`domain:update`/explicitly-approved `domain:delete` scopes. No broad `api:write` requirement is introduced. Checkpoint 3 validation uses injected mock transport only and makes no DigitalOcean, application, or DNS call. Real routing and recovery fixtures remain checkpoint 4 work and remain fail closed through the existing unavailable routing-control implementation until separately authorized.

## Phase 7B routing control — checkpoint 4 (2026-08-20)

Checkpoint 4 implements the existing four-operation routing-control contract over the checkpoint-3 client; it does not add a second interface or broaden routing into worker, authority, or coordinator policy. `ProductionDigitalOceanRoutingControl.js` controls exactly one configured CNAME inside an already-prepared DigitalOcean zone. The accepted production resource identity is zone `cutover.dustinginn.com`, leaf `app.cutover.dustinginn.com`, record type `CNAME`, and expected switch TTL 60 seconds. The adapter still requires explicit injected zone/leaf/Windows-target/provider-target/TTL configuration; the unresolved live Windows custom-edge and App Platform alias values are not hard-coded. It never creates the zone, attaches an App custom domain, chooses a target, or queries public DNS.

**Inspection and strict state identity.** Every operation first reads the exact zone and lists the exact leaf without filtering away an unexpected record type. One exact record ID, supported CNAME type, expected target role, and exact TTL are required. Missing zone/record is `unprepared`; unavailable reads are `ambiguous`; an unapproved target, multiple records, wrong type, wrong returned name/ID, or TTL drift is explicit and fail closed. Trailing-dot and case normalization are the only target normalization. Target strings are treated as non-secret infrastructure configuration but evidence records only `windows`/`provider`/`unexpected` roles, not raw values. TTL is strict because an unexpectedly long cache lifetime materially changes cutover and legal pre-M recovery timing; it is not treated as cosmetic provider normalization.

**One mutation, then readback.** Provider activation is legal only from exact Windows state; pre-M restoration is legal only from exact provider state. Already-exact state is an idempotent read-only success. Otherwise, the adapter submits one `updateDomainRecord` with a caller operation/command identity and never retries it.
